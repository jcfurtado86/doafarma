## Epic 1: Destravar Onboarding e Blindar Autenticação

### Hypothesis

We believe that **eliminar a aprovação manual para receptores, automatizar a validação de médicos via API do CFM e proteger endpoints de autenticação** para **receptores, médicos e admins** will achieve **redução de 80% no tempo entre cadastro e primeiro uso do app** because a discovery identificou que "aprovação manual é gargalo" para admins (Persona Admin — §3), receptores "não precisam de aprovação" (Decisão #3 — §7), e a analogia "entre um Banco do Brasil da vida digital e um Nubank, eu prefiro muito mais o Nubank" reforça preferência por onboarding instantâneo.

### Goal

Todo receptor consegue usar o app imediatamente após o cadastro, e todo médico com CRM válido é aprovado automaticamente em menos de 1 minuto.

### Scope In

- Remover barreira de aprovação para receptores, ativando conta imediatamente no cadastro (E2)
- Integração com API/portal do CFM para validar CRM automaticamente (D1)
- Auto-aprovação de médico quando CRM é validado com sucesso (E1)
- Rate limiting nos endpoints de login e reset de senha (D4)
- Implementar reset de senha no app mobile (D4)

### Scope Out

- Upload de documentos para validação manual de médico (fallback se API do CFM não existir — tratar como risco)
- Validação de outros campos do cadastro (CPF, endereço)
- Fluxo de re-aprovação ou suspensão de médicos já aprovados
- Multi-factor authentication

### Success Criteria

1. **Given** um novo receptor completou o cadastro, **When** o cadastro é salvo, **Then** o receptor pode acessar todas as funcionalidades do app imediatamente sem aguardar aprovação
2. **Given** um novo médico preencheu CRM e UF no cadastro, **When** o sistema consulta a API do CFM, **Then** o médico é aprovado automaticamente se o CRM for válido, ou rejeitado com mensagem clara se for inválido
3. **Given** um atacante tenta brute force no login, **When** faz mais de 5 tentativas em 1 minuto, **Then** as requisições seguintes são bloqueadas por rate limiting
4. **Given** um usuário esqueceu a senha, **When** acessa "Esqueci minha senha" no app mobile, **Then** recebe email com link para redefinir a senha

### Priority

**P0** — Elimina o maior gargalo de onboarding e corrige vulnerabilidade de segurança classificada como P0 na auditoria.

### Size

**M** (3-7 dias) — E2 é trivial (remover middleware), D4 é pequeno (rate limiter + tela), E1+D1 é médio (integração com API externa).

### Dependencies

- **Externa**: Existência de API acessível do CFM para validação de CRM (risco identificado na discovery §6)

### Risks

1. **Risk**: API do CFM pode não existir ou não ser acessível gratuitamente
   **Mitigation**: Pesquisar alternativas (web scraping do portal, base de dados pública). Se nenhuma opção gratuita existir, implementar validação manual como fallback temporário mantendo auto-aprovação como objetivo.

2. **Risk**: Remover aprovação de receptor pode permitir cadastros falsos/spam
   **Mitigation**: Rate limiting na criação de conta + monitoramento no painel admin. Se necessário, adicionar verificação de email.

### Sequence

**Now** — Sem dependências internas. Desbloqueia Epic 4 (selo verificado depende de CRM validado).

## Epic 2: Estabelecer Design System e Consistência Visual

### Hypothesis

We believe that **definir um design system unificado e padronizar a navegação e estados vazios** para **médicos e receptores** will achieve **experiência visual consistente que elimina a percepção de app "confuso ou feio"** because a auditoria identificou que a tela do médico tem "botões soltos" vs tab navigation do receptor (gap #20 — §3 Persona Médico), e a entrevista revelou que "app confuso ou feio" é motivo de saída para médicos.

### Goal

Todas as telas do app seguem o mesmo design system, e médicos e receptores têm experiência de navegação equivalente.

### Scope In

- Definição de design tokens (cores, tipografia, espaçamentos, elevações) baseado em inspirações do Kauê (B1)
- Biblioteca de componentes reutilizáveis (botões, cards, inputs, modais) (B1)
- Refatorar navegação do médico para tab navigation, equivalente ao receptor (B2)
- Implementar telas de estado vazio para todas as listas do app (B3)

### Scope Out

- Redesign geral de todas as telas (B4 — P2, depende do design system estar maduro)
- Animações e micro-interações
- Dark mode
- Testes de usabilidade com usuários reais

### Success Criteria

1. **Given** o design system está definido, **When** um desenvolvedor precisa criar uma nova tela, **Then** pode usar componentes da biblioteca sem criar estilos ad-hoc
2. **Given** um médico abre o app, **When** navega entre seções, **Then** a navegação usa tabs na parte inferior, idêntica à experiência do receptor
3. **Given** um receptor não tem medicamentos solicitados, **When** acessa a lista de solicitações, **Then** vê uma tela de estado vazio com ilustração e ação sugerida
4. **Given** qualquer lista no app está vazia, **When** o usuário acessa essa tela, **Then** vê um estado vazio informativo ao invés de uma tela em branco

### Priority

**P0** — Desbloqueia todo trabalho visual futuro e evita retrabalho. Discovery §5 classificou como P0 (RICE 8.0).

### Size

**M** (3-7 dias) — Design tokens e componentes base (2-3 dias), refatoração de navegação (1-2 dias), estados vazios (1-2 dias).

### Dependencies

- Nenhuma — pode ser iniciado independentemente.

### Risks

1. **Risk**: Design system criado sem referência visual clara pode resultar em inconsistência
   **Mitigation**: Usar referências visuais que o Kauê já tem em mente (citado na entrevista). Definir tokens mínimos primeiro e iterar.

2. **Risk**: Refatorar navegação do médico pode quebrar fluxos existentes
   **Mitigation**: Mapear todos os fluxos do médico antes de refatorar. Manter rotas existentes funcionais durante a migração.

### Sequence

**Now** — Sem dependências. Pode ser desenvolvido em paralelo com Epics 1 e 3.

## Epic 3: Habilitar Autogestão de Conta e Endereços

### Hypothesis

We believe that **permitir que usuários gerenciem seus endereços e dados pessoais após o cadastro** para **médicos e receptores** will achieve **aumento nas doações concluídas por mês** because a auditoria identificou que o médico "não consegue atualizar endereço depois do cadastro" (§3 Persona Médico) e o bug silencioso do `->first()` no endereço impede o fluxo de encontro funcionar corretamente (A1 — auditoria gap #2).

### Goal

Médicos e receptores conseguem cadastrar, editar e selecionar endereços, e definir um local padrão para encontros de doação.

### Scope In

- CRUD de endereços no app mobile (criar, listar, editar, excluir) (A1)
- Definir endereço padrão para encontros (A1)
- Opção de alterar local em cada agendamento específico (A1)
- Tela de configurações pessoais (editar nome, telefone, email) (A3)

### Scope Out

- Validação de endereço via API de CEP (usar input manual)
- Mapa interativo para seleção de endereço
- Geolocalização automática (H1 — Epic 5)
- Busca por proximidade geográfica (H1 — Epic 5)

### Success Criteria

1. **Given** um médico logado, **When** acessa "Meus Endereços", **Then** pode cadastrar um novo endereço com rua, número, bairro, cidade, UF e CEP
2. **Given** um médico com múltiplos endereços, **When** marca um como padrão, **Then** esse endereço é sugerido automaticamente em novos agendamentos
3. **Given** um agendamento em andamento, **When** o médico propõe um local, **Then** pode escolher entre seus endereços cadastrados ou inserir um local diferente
4. **Given** um receptor logado, **When** acessa "Configurações" e edita seu nome, **Then** a alteração é salva e refletida em todo o app

### Priority

**P0** — Corrige bug silencioso do `->first()` e desbloqueia o fluxo de encontro, diretamente ligado à north star (doações concluídas).

### Size

**M** (3-7 dias) — CRUD endereços backend + mobile (3-4 dias), tela de configurações (1-2 dias).

### Dependencies

- Nenhuma — pode ser iniciado independentemente.

### Risks

1. **Risk**: Múltiplos endereços por usuário pode complicar a lógica de agendamento existente
   **Mitigation**: Manter compatibilidade com agendamentos existentes usando endereço padrão como fallback.

2. **Risk**: Edição de email pode quebrar autenticação
   **Mitigation**: Exigir confirmação de senha ao alterar email. Enviar verificação para o novo email antes de efetivar a troca.

### Sequence

**Now** — Sem dependências. Desbloqueia Epic 5 (geolocalização depende de endereços cadastrados).

## Epic 4: Construir Confiança e Transparência

### Hypothesis

We believe that **tornar visíveis as credenciais dos médicos, permitir denúncias e exibir fotos dos medicamentos** para **receptores** will achieve **aumento na taxa de aceitação de doações** because a entrevista revelou que "insegurança no encontro" é motivo de saída (§3 Persona Médico), e receptores não têm como avaliar a confiabilidade do médico antes de solicitar (§3 Persona Receptor — "processo inseguro de encontro").

### Goal

Receptores conseguem visualizar o perfil verificado do médico com avaliações antes de solicitar, e qualquer usuário pode denunciar comportamento inadequado.

### Scope In

- Perfil público do médico com selo "CRM Verificado", nota média e avaliações visíveis (D2)
- Sistema de denúncia com categorias (medicamento inadequado, comportamento, não-comparecimento) (D3)
- Fluxo de consequências para denúncias (aviso, suspensão, banimento) gerenciado pelo admin (D3)
- Upload de foto do medicamento no momento do cadastro da oferta (A2)

### Scope Out

- Chat entre médico e receptor (H4 — P2)
- Verificação de identidade além do CRM (biometria, documento com foto)
- Moderação automática de fotos via IA
- Sistema de reputação com badges/níveis

### Success Criteria

1. **Given** um receptor visualiza uma oferta de medicamento, **When** toca no nome do médico, **Then** vê o perfil público com selo "CRM Verificado", nota média e últimas avaliações
2. **Given** um receptor teve uma experiência negativa, **When** acessa a opção "Denunciar" no perfil do médico, **Then** pode selecionar uma categoria e descrever o ocorrido
3. **Given** um admin recebe uma denúncia no painel, **When** analisa e decide aplicar suspensão, **Then** o médico é notificado e tem acesso restrito até resolução
4. **Given** um médico cadastra uma oferta de medicamento, **When** preenche os dados, **Then** pode tirar ou anexar uma foto do medicamento

### Priority

**P1** — Aumenta confiança na plataforma, mas depende da validação de CRM do Epic 1.

### Size

**M** (3-7 dias) — Perfil público (2 dias), denúncias (2-3 dias), upload de foto (1-2 dias).

### Dependencies

- **Epic 1** — validação de CRM habilita o selo "CRM Verificado"

### Risks

1. **Risk**: Denúncias falsas podem prejudicar médicos legítimos
   **Mitigation**: Implementar fluxo de análise manual pelo admin antes de aplicar consequências. Médico pode contestar.

2. **Risk**: Upload de imagens aumenta custo de armazenamento
   **Mitigation**: Usar compressão de imagem no cliente, limitar a 1 foto por oferta, e usar storage gratuito (ex: Cloudinary free tier) para manter orçamento zero.

### Sequence

**Next** — Depende de Epic 1 para selo verificado.

## Epic 5: Engajar com Notificações Inteligentes e Busca Geográfica

### Hypothesis

We believe that **enviar notificações proativas personalizadas e permitir busca por proximidade geográfica** para **receptores** will achieve **aumento significativo nas doações concluídas por mês** because a entrevista revelou que receptores querem um "app que cuida de mim — monitora condições, notifica quando medicamento que precisa está disponível" (§3 Persona Receptor) e "sem busca por proximidade geográfica" é dor mapeada.

### Goal

Receptores recebem notificações quando medicamentos relevantes ficam disponíveis perto deles, e podem filtrar ofertas por distância.

### Scope In

- Notificações proativas quando medicamento de interesse fica disponível (C2)
- Perfil de necessidades do receptor (condições/medicamentos recorrentes) para personalizar notificações (H3)
- Busca de ofertas por proximidade geográfica com filtro de raio (H1)
- Ordenação de resultados por distância

### Scope Out

- App como "companheiro de saúde" com monitoramento completo (C1 — P2)
- Notificações de marketing ou engajamento genérico
- Rastreamento de localização em tempo real
- Integração com mapas interativos na primeira versão

### Success Criteria

1. **Given** um receptor cadastrou "Losartana" como medicamento de interesse, **When** um médico cadastra uma oferta de Losartana, **Then** o receptor recebe push notification em até 5 minutos
2. **Given** um receptor acessa a lista de ofertas, **When** ativa o filtro "Perto de mim", **Then** vê apenas ofertas dentro do raio configurado, ordenadas por distância
3. **Given** um receptor com perfil de necessidades preenchido, **When** novos medicamentos compatíveis são cadastrados, **Then** recebe notificações apenas dos medicamentos relevantes (sem spam)

### Priority

**P1** — Alto impacto na retenção e na north star metric, mas requer infraestrutura de endereços do Epic 3.

### Size

**L** (1-2 semanas) — Geolocalização com cálculo de distância (3-5 dias), sistema de notificações personalizadas (3-5 dias), perfil de necessidades (1-2 dias).

### Dependencies

- **Epic 3** — endereços cadastrados são base para cálculo de distância

### Risks

1. **Risk**: Cálculo de geolocalização pode ser complexo de configurar no ambiente atual
   **Mitigation**: Começar com cálculo simples de distância via fórmula Haversine, sem extensões especializadas. Migrar para soluções otimizadas só se performance exigir.

2. **Risk**: Excesso de notificações pode irritar usuários e causar desinstalação
   **Mitigation**: Limitar a 3 notificações por dia por receptor. Permitir configurar frequência e desativar por categoria.

3. **Risk**: Poucos medicamentos na plataforma podem tornar filtro geográfico inútil (resultados vazios)
   **Mitigation**: Quando filtro geográfico retorna vazio, sugerir ampliar raio ou mostrar opções mais distantes. Implementar estado vazio útil (Epic 2).

### Sequence

**Next** — Depende de Epic 3 para endereços.

## Epic 6: Empoderar Painel Administrativo

### Hypothesis

We believe that **dar ao admin CRUD completo de todas as entidades do sistema** para **admins** will achieve **eliminação de queries manuais no banco de dados para operações do dia a dia** because a auditoria e entrevista identificaram que o admin "não consegue gerenciar base de medicamentos nem avaliações pelo painel" (§3 Persona Admin) e hoje depende de acesso direto ao banco.

### Goal

O admin consegue visualizar, criar, editar e excluir todas as entidades do sistema pelo painel web sem acessar o banco diretamente.

### Scope In

- Gestão de medicamentos da base oficial pelo painel (E3)
- Gestão de avaliações/ratings pelo painel (E3)
- Gestão de ofertas de medicamentos pelo painel (E3)
- Gestão de solicitações e agendamentos pelo painel (E3)

### Scope Out

- Multi-admin com papéis e permissões (E4 — P2, prematuro para escala atual)
- Dashboard com analytics avançados
- Exportação de relatórios
- Gestão de notificações pelo painel

### Success Criteria

1. **Given** um admin logado no painel, **When** acessa "Medicamentos", **Then** pode listar, buscar, criar, editar e excluir medicamentos da base
2. **Given** um admin visualiza uma avaliação, **When** decide que o conteúdo é inadequado, **Then** pode editar ou remover a avaliação
3. **Given** um admin precisa investigar uma doação, **When** busca por oferta ou solicitação, **Then** encontra todos os dados relevantes (médico, receptor, medicamento, status, histórico)

### Priority

**P1** — Melhora eficiência operacional, mas não bloqueia a north star metric.

### Size

**M** (3-7 dias) — Resources do painel admin são rápidos de criar com o boilerplate existente. 4-5 entidades com ~1 dia cada.

### Dependencies

- Nenhuma — pode ser iniciado independentemente.

### Risks

1. **Risk**: Admin com poder de editar/excluir tudo pode causar danos acidentais
   **Mitigation**: Implementar soft-delete em todas as entidades. Log de atividades do admin no painel.

### Sequence

**Next** — Sem dependências técnicas, mas menor prioridade que Epics 4 e 5.
